Four detailed reports sit in [audit-2026-09-20/](audit-2026-09-20/): [web](audit-2026-09-20/web.md), [pipeline and data](audit-2026-09-20/pipeline-and-data.md), [API and operations](audit-2026-09-20/api-and-operations.md), [iPhone and backlog](audit-2026-09-20/iphone-and-backlog.md).

## What runs today, proven

- `pnpm test`: **361 tests, 360 pass.** query 111, api 68, pipeline 113, web 68 of 69. The one failure is a missing file, explained below.
- `pnpm build:bundle` produces a current, signed bundle (dev key): 418 listings, 52 greenway segments, 302 parks, 205 neighborhoods, 29 files, all checksummed.
- The Worker was run locally against its four migrations and driven end to end: a report was deduplicated per phone per day, reached the steward queue, was archived, and the counts flowed back. Its zero-PII rules held under live testing: an unknown field is rejected, free text is masked, condition reports keep only the hour, and no IP or identifier reaches the database.
- The iPhone app builds and runs in the simulator, verifies the signed bundle offline, and its shared rules library passes all 111 fixture cases.

## What is written down but not built

**Nothing runs on a schedule.** The nightly publish, the page re-check that raises steward tasks, the 180-day report purge and the 30-day photo delete are all code that has never executed. They need a deployed Worker and a workflow runner.

**This checkout is not a git repository.** There is no `.git` and no `.github/`. The publish workflow and CI that five documents describe are not here, `apps/ios/README.md`'s "CI runs the Swift tests on every push" cannot be true here, and the one failing test fails only because it looks for `.github/workflows/publish.yml`. The bundle's own version string starts with `nogit-`. This is the single biggest gap between the docs and this working copy, and it also means the "an open-data change arrives as a pull request a steward merges" model has nothing behind it right now.

**Six things block a deploy** (`pnpm preflight`): two pinned public keys, a release signing key, a real D1 database id, the live site's origin, and the Cloudflare Access settings. Preflight cannot see two things it depends on most — the Access policy and the rate-limit rule — so a checkout could pass every check and still deploy an unprotected API.

**Rate limiting exists only as a comment.** By decision it lives in a Cloudflare rule rather than code, and that rule does not exist yet. Today the only abuse defense is one report per phone per listing per day.

**Three screens are code-only because their data is empty:** alerts (0), archived listings (0, so "closed places" can never appear in search), and City events, which were dropped and left the Events tab as dead code.

**Seven categories have no listings:** warming and cooling centers (alert-driven, expected), safer-use supplies, Health Department programs, rides, walk-in treatment and recovery support.

**Photos and the sunset banner are built and switched off**, which is correct but means neither has been exercised.

## Two bugs found and fixed during the audit

1. **The About screen would have printed a raw key.** Its paragraphs are built in a numbered loop, and removing the "not an official City app" line yesterday left a hole, so the screen would have shown the literal text `about.p3`. Paragraphs renumbered; a test now ties the loop to the strings.
2. **The tab bar reserved five columns for four tabs**, leaving an empty slot and shifting the tabs left on every screen, since Events hid itself in TypeScript only. The bar now sizes itself to however many tabs show; a test guards it.

## Docs that no longer match the code

Stale in the bad direction: a DECISIONS row still says the nightly re-check and steward tasks are "not built" (both exist and pass tests); docs/06 says the app shows a "reporting available" indicator from `/v1/health` (it never calls it); docs/05 still says four shortcuts on Home (there are six) and shows five tabs; docs/03 lists bundle files that are never produced; docs/04 says the urgent-numbers file has six rows (it has eleven).

Stale in the good direction: food-poor neighborhoods are 29 of 205, not 93; listings are 418, not 178; shower listings 4, not 2; listings needing a by-eye check 24, not 33; and the install-key reset button that docs/08 calls unbuilt is live.

Also worth knowing: the committed greenway access report is from an older bundle (49 listings, 18 segments flagged) and understates today's coverage (114 listings, 16 flagged, 3 segments with nothing nearby), and `help.coverage_checked` on neighborhood pages can never be true, because the build never passes that flag.
